# RecipeWeaver development artifacts

SHA-256: `3BB76E0EC30CEF39D16AA29B272394978EED130054B7DF14C05DDA10F00B72C8`

For a development server, install only that RecipeWeaver JAR in `plugins`. The separate `RecipeWeaverSmoke-*.jar` is **test-only** and shuts the server down after its checks. Never include it in a production installation. RecipeWeaver is authored by TM Game Studio. No numbered milestone or production release is complete yet; see [the build plan](../BUILD_PLAN.md).

The retained 0.2.70 through 0.2.73 JARs passed their stated automated checks, but each contains fewer than the then-required 35 substantive new features or bug fixes. Earlier development builds also have no verified 35-change ledger, so no historical JAR is claimed to satisfy that earlier per-release requirement. These remain intermediate builds. Versions 0.2.74 through 0.2.82 have [35](0.2.74-CHANGE-LEDGER.md), [40](0.2.75-CHANGE-LEDGER.md), [39](0.2.76-CHANGE-LEDGER.md), [46](0.2.77-CHANGE-LEDGER.md), [51](0.2.78-CHANGE-LEDGER.md), [36](0.2.79-CHANGE-LEDGER.md), [36](0.2.80-CHANGE-LEDGER.md), [37](0.2.81-CHANGE-LEDGER.md), and [52](0.2.82-CHANGE-LEDGER.md) individually verified changes respectively. Version 0.2.83 has [81](0.2.83-CHANGE-LEDGER.md) individually verified changes under the 75-change rule. Versions 0.2.84, 3.6, and 3.7 are focused intermediate hotfixes, while 3.5 is a version-only build. None satisfies the 75-change gate. The next full production release requires at least 75 new, distinct, substantive production changes after 3.7, each with its own executed focused test or live assertion. Current unreleased work is tracked in [NEXT_RELEASE_WORK.md](../NEXT_RELEASE_WORK.md).

## 0.2.59 SQL mirror conflict and propagation rules

- On startup or selection, a nonempty SQL mirror that differs from local files pauses with a conflict status. A full retry compares the complete SQL copy with the last synchronized copy; live writes compare the affected SQL path before changing it. A conflict leaves local writes intact and does not auto-retry an overwrite. Each selected mirror reports its own status, so a healthy second mirror can continue.
- The SQL source order menu offers two audited choices for a selected SQL copy. Left click prepares the inspected SQL data as a reviewable backup for the existing restore confirmation. Right click opens a confirmation to keep local files and replace that SQL copy. `RecipeWeaverApi.replaceSqlMirrorFromLocalAsync(mode, expectedSha256)` rejects an inspection hash that no longer matches. Ordinary mirror retries do not override a conflict. Explicit manual SQL export still replaces its target, and its verified contents become the active mirror's new baseline.
- A mirror's known baseline survives selection changes, reload, and confirmed restore in the same server run. A local restore can propagate when the SQL copy still matches that baseline; an independently changed SQL copy remains paused. Unit tests cover startup divergence, path changes, full resync divergence, stale inspection, mirror isolation, and restore reconfiguration.
